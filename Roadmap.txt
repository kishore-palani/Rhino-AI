# AI RHINO ARCHITECT

## AI-Powered Architectural Design & Computational Modeling Agent for Rhino + Grasshopper

**Target Development Environment:** VS Code
**AI Coding Agent:** Kilo AI
**Primary CAD Platform:** Rhino 3D
**Parametric Platform:** Grasshopper
**Initial Goal:** Build a working V0.1 AI agent capable of converting natural-language instructions into validated Rhino geometry, accepting user feedback, correcting the design, and storing the resulting experience.

---

# 1. PROJECT VISION

Build an AI-powered architectural design agent that works inside or alongside Rhino and Grasshopper.

The system should eventually understand:

* Natural language
* Architectural design intent
* Spatial planning
* Building components
* Dimensions
* Construction methods
* Building regulations
* Computational design
* Rhino modeling
* Grasshopper workflows
* Images
* Sketches
* Videos
* Architectural precedents
* Fabrication requirements
* 3D concrete printing
* User feedback
* Modeling failures
* New architectural trends

The long-term system should be capable of:

> **Understanding an architectural problem → reasoning about the design → generating a modeling strategy → executing it in Rhino → validating the result → receiving feedback → modifying the design → learning from the result.**

This is NOT simply a text-to-3D generator.

It is intended to become an:

> **AI Architectural Computational Design Agent.**

---

# 2. CORE DESIGN PHILOSOPHY

The system should not be designed around the assumption that architecture is a collection of predefined shapes.

Instead, architecture should be represented as relationships:

```text
USER INTENT
      ↓
FUNCTION
      ↓
SPATIAL RELATIONSHIPS
      ↓
DESIGN STRATEGY
      ↓
PARAMETERS
      ↓
GEOMETRY
      ↓
CONSTRUCTION
      ↓
FABRICATION
```

The AI must be able to explore new possibilities.

Do not restrict it to copying existing architectural styles.

Do not hard-code one architectural methodology.

Do not train it only on final images.

The system should learn from:

* Process
* Decisions
* Alternatives
* Failures
* Corrections
* Feedback
* Successful solutions

# 3. PRIMARY V0.1 OBJECTIVE

Do NOT attempt to build the complete AI architect initially.

The first version must prove this loop:

```text
USER
 ↓
TEXT REQUEST
 ↓
LLM
 ↓
DESIGN INTENT
 ↓
MODELING PLAN
 ↓
MODELING SKILLS
 ↓
RHINO TOOL CALLS
 ↓
RHINO GEOMETRY
 ↓
GEOMETRY VALIDATION
 ↓
RESULT
 ↓
USER FEEDBACK
 ↓
AI CORRECTION
 ↓
UPDATED MODEL
 ↓
STORE EXPERIENCE
```

Example:

User:

> Create a 5m × 4m room with 200mm walls, a 900mm door on the south wall and a 1500mm window on the east wall.

The AI should:

1. Parse the request.
2. Identify units.
3. Identify geometry.
4. Create a modeling plan.
5. Call the appropriate modeling skills.
6. Create the geometry in Rhino.
7. Validate it.
8. Report the result.
9. Allow the user to modify it.

# 6. COMPONENT B — AI ORCHESTRATOR

The orchestrator is the brain responsible for deciding:

* What the user wants.
* What information is missing.
* Which knowledge is relevant.
* Which modeling skill should be used.
* Which Rhino tools should be called.
* Whether validation is required.
* Whether the result is successful.
* Whether another iteration is necessary.

It should NOT directly manipulate Rhino geometry wherever possible.

Instead:

```text
LLM
 ↓
Structured plan
 ↓
Skill selection
 ↓
Tool call
 ↓
Rhino
```

# 12. RHINO TOOL LAYER

The AI should see a controlled set of tools.

Example:

```json
{
  "name": "create_wall",
  "description": "Create a wall from a baseline curve",
  "parameters": {
    "curve": {},
    "height": {},
    "thickness": {}
  }
}
```

The LLM should never need to know the internal implementation of the tool.

It only needs to know:

* What the tool does.
* What inputs it requires.
* What it returns.
* What errors may occur.

# 14. GEOMETRY VALIDATION

The system must not assume that successful code execution means successful geometry.

Create a validation layer.

Check:

* Valid Brep
* Closed solids
* Self intersections
* Duplicate objects
* Zero-length curves
* Invalid surfaces
* Object dimensions
* Intersections
* Units
* Expected object count
* Bounding box
* Required relationships

Example:

```text
CREATE WALL
     ↓
RHINO RESULT
     ↓
VALIDATE
     ├── valid
     └── invalid
           ↓
        diagnose
           ↓
        correct
```

# 50. KILO AI OPERATING INSTRUCTIONS

Kilo AI should follow these rules while developing the project.

## Rule 1 — Research before implementation

If a technical question concerns current Rhino APIs, AI APIs, MCP, model capabilities, or external libraries, verify current documentation before implementing.

## Rule 2 — Do not hallucinate APIs

Never invent:

* Rhino methods
* Grasshopper methods
* MCP tools
* AI APIs
* package APIs

Verify them.

## Rule 3 — Keep components modular

Do not create one giant application file.

## Rule 4 — Keep AI provider independent

Use provider interfaces.

## Rule 5 — Never expose API keys

Use environment variables.

## Rule 6 — Validate generated geometry

Never assume successful tool execution means valid geometry.

## Rule 7 — Preserve user control

The AI should propose or execute actions through controlled tools.

## Rule 8 — Store structured experiences

Do not save entire conversations as the only form of memory.

Extract:

* Task
* Intent
* Action
* Result
* Feedback
* Failure
* Correction

## Rule 9 — Do not automatically fine-tune

Build the dataset first.

## Rule 10 — Do not hard-code architectural style

The AI should be capable of exploring different architectural approaches.

# 53. FINAL DEVELOPMENT PRINCIPLE

The goal is not:

> **Build an LLM that knows Rhino commands.**

The goal is:

> **Build an AI system that understands architectural intent and uses Rhino as its precise computational design environment.**

The distinction is fundamental.

The LLM provides:

```text
Reasoning
Planning
Language
Knowledge retrieval
Decision making
```

The specialized systems provide:

```text
Rhino → Geometry
Grasshopper → Parametric logic
Database → Structured knowledge
Vector DB → Semantic retrieval
Knowledge graph → Relationships
Rule engine → Constraints
Validation engine → Verification
Memory → Experience
Video models → Process understanding
Vision models → Visual understanding
```

Together they form the **AI Architectural Design Agent**.
